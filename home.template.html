Un IMSI. Deux réseaux. Zéro antenne.

Une image Ubuntu 22.04 (noyau 6.8) qui démarre, seule, un réseau 2G/GPRS Osmocom complet — SS7, deux cellules DCS1800, un baseband TI Calypso émulé qui exécute le vrai firmware OsmocomBB — et un cœur 4G/LTE open5gs + srsRAN, reliés par un lien SGs. Au bout : un téléphone postmarketOS, data en LTE, voix et SMS en GSM, sur la même identité. Aucune radio à brancher : le lien radio est une socket.

La carte du banc

Tout ce qui tourne, et ce qui relie tout.

Deux plans complets, un pont entre eux, un téléphone en bas qui parle aux deux. Cliquez n'importe quel bloc : les ports, les point codes et les compteurs relevés sur le banc s'affichent dessous.

Le banc, en une phrase

srsUE + postmarketOS · IMSI 001010001000001 · MSISDN 100101

  • Le même abonné est attaché des deux côtés : attach combiné EPS+IMSI par SGsAP côté LTE, présence radio côté GSM sur la cellule 6001.
  • Un appel entrant vers 100101 arrive au MSC, le MME page l'UE, l'UE redescend sur la BTS. C'est ça, le CSFB, et les deux extrémités sont en place.
  • Cliquez un bloc de la carte pour le détail : ports, point codes, identifiants de cellule, compteurs.

Les blocs violets sont les trois pièces qui font la singularité du banc : le baseband Calypso émulé, le lien SGs, et le téléphone postmarketOS.

Couche 1

Un vrai Calypso, émulé.

C'est la partie qui distingue ce banc d'un lab Osmocom ordinaire : il n'y a ni SDR ni téléphone physique. QEMU émule le SoC TI Calypso, le firmware OsmocomBB s'exécute dessus, et les bursts remontent jusqu'à la BTS par un pont en Python.

La chaîne, de bas en haut

Les plans, un par un

Relevé sur la machine, pas sur le papier.

Signalisation SS7

osmo-stp en SCTP sur 127.0.0.1:2905 (M3UA). Deux ASP établis : osmo-bsc depuis :2907, osmo-msc depuis :2906 — ESTAB vérifiés dans ss. Point code 2057 côté MSC.

Le seul incident au démarrage — N-NOTICE.ind cause='MTP failure' à 21:10:27 — est la course habituelle BSC-avant-STP, résorbée d'elle-même.

Voix

Le MSC est en MNCC externe sur /tmp/msc_mncc → Asterisk (SIP 5060, codecs mncc-int tch-f fr / tch-h hr). osmo-sip-connector sur 127.0.0.1:5061, osmo-mgw en MGCP 2427.

SMS

sms-over-gsup : les SM-RP partent au HLR, puis au proto-smsc-daemon (SMSC-OP1, 127.0.0.2). SMPP 2775 en smpp-first, ESME msc_tester, avec les quatre formes de numérotation de 100101 routées (unknown/unknown, unknown/isdn, national/isdn, international/isdn).

sms-interop-relay.py sur 7890 fait le lien inter-opérateurs.

Le commentaire de config qui dit pourquoi

« Le téléphone pmOS est l'abonné 100101, au même titre que le mobile osmocom-bb, et on veut que les deux sonnent. »

Autrement dit : un SMS entrant arrive par l'ESME SMPP et est dupliqué vers le mobile osmocom-bb par le VTY — OSMO_SMS_DUPLIQUE=1.

Sécurité NAS — nulle, et volontairement

Et l'abonné du CSFB est identifiable : srsue porte l'IMSI 001010001000001, c'est-à-dire exactement l'abonné #01 du cache MSC → MSISDN 100101, TMSI 17CC99EC, actuellement attaché sur GERAN-A, cellule 6001.

Le même abonné est enregistré des deux côtés : attach combiné EPS+IMSI par SGsAP côté LTE, présence radio côté GSM. Un appel entrant vers 100101 → le MSC page par le MME → l'UE redescend sur la BTS.

L'abonné #00 (100102, IMSI …002, cellule 6012, BTS 1) est le correspondant : le banc est câblé pour un appel 100101 → 100102, inter-cellule, avec fallback.

Le problème, et le patch

Le noyau linux-postmarketos-stable x86_64 a, en amont, # CONFIG_PPP is not set. Sans PPP, un modem AT ne peut pas transporter d'IP : pas de data sur le téléphone. patches/pmaports-linux-postmarketos-stable-ppp.patch corrige exactement ça :

-# CONFIG_PPP is not set
+CONFIG_PPP=m
+CONFIG_PPP_BSDCOMP=m
+CONFIG_PPP_DEFLATE=m
+CONFIG_PPP_FILTER=y
+CONFIG_PPP_MULTILINK=y
+CONFIG_PPP_ASYNC=m
+CONFIG_PPP_SYNC_TTY=m

(+ la somme de contrôle config-stable.x86_64 dans l'APKBUILD, sans quoi abuild refuse.)

Recompiler un noyau pmOS à chaque build d'ISO serait rédhibitoire : iso_modules/88-lte-pmos.sh télécharge un .deb prébuilt via Git LFS — osmo-build-pmos-kernel_7.2.3.0+pp-noble_amd64.deb depuis bbaranoff/pmos_ppp_kernel — et le pose dans /usr/lib/user_interface/kernel/pmos/ (avec APKINDEX.tar.gz, vérifié par chk du module). Second patch, pmbootstrap-qemu-bench.patch (15 Ko), injecte dans pmbootstrap les options QEMU du banc.

La 4G du téléphone — PPP → bearer LTE

pmOS : NetworkManager → pppd (ATD*99***1#, CONNECT)
↓ virtio-console → osmo.data → 127.0.0.1:12347
hôte : osmo-phonesim-banc.py --connect → interface ppp-pmos
↓ 10.99.0.1 ↔ 10.99.0.2, DANS la netns ue1
tun_srsue 10.45.0.2 → srsUE → srsENB → open5gs UPF → MASQUERADE → Internet

Vérifié : ip netns exec ue1 ip route montre 10.99.0.2 dev ppp-pmos src 10.99.0.1 à côté de la route par défaut dev tun_srsue. Le trafic data du téléphone transite bien par le bearer LTE. Les rugosités sont notées : IPv6CP et CCP refusés en Protocol-Reject, et une fois pppd lancé, plus rien d'AT ne doit être écrit sur le port (un RING ou un +CMTI émis là partirait dans le flux PPP).

La 2G du téléphone — voix et SMS

Seconde virtio-console, osmo.modem = 127.0.0.1:12346, où osmo-phonesim-banc.py tient le rôle du modem :

« oFono ne fabrique pas de modem : il en PILOTE un. Sur ce banc il n'y a pas de dongle — l'EC25, pour nous, c'est oFono. » commentaire d'en-tête, osmo-phonesim-banc.py

Le programme répond en AT 27.007 en lisant les VTY du banc : osmo-bsc:4242 (MCC/MNC, ARFCN, état d'enregistrement), osmo-msc:4254, mobile:4247. Un banc arrêté = un modem « non enregistré » : c'est la vérité, pas une panne.

Audio : deux chaînes PulseAudio duplex sur le QEMU — gsm_mic / gsm_audio.monitor (le pont audio du mobile osmocom-bb, via GAPK) et osmo_hp_ec / osmo_mic_ec (avec annulation d'écho), chacune sur son intel-hda + hda-duplex.

osmo-ril-atmodem.py tourne aussi, mais c'est un vestige assumé : écrit pour le RIL d'un Android sous Waydroid, abandonné depuis, il reste le port AT adossé à oFono, exposé dans /run/osmo-ril/at-pty.

Le résultat

Le téléphone pmOS est data en 4G, voix et SMS en 2G, sur la même identité (IMSI 001010001000001 / 100101) — c'est-à-dire le comportement d'un vrai terminal CSFB, réalisé au niveau du modem, avec un noyau dont on a dû rallumer PPP pour que ce soit possible.

Démarrage rapide

Commencez par le 600.

Dans Linphone, composez un numéro et décrochez. Si le 600 vous répond, la chaîne SIP et l'audio sont bonnes. Ensuite, appelez 100101 : c'est le téléphone.

NuméroDestination
100Linphone A
200Linphone B
600Test d'écho, votre voix vous revient
500 / 700Annonces enregistrées
100101Abonné #01 — srsUE + pmOS, cellule 6001
100102Abonné #00 — mobile osmocom-bb, cellule 6012

Depuis un mobile, tout passe par le VTY de la console web : choisissez l'opérateur, le mobile, puis Go.

OsmoMobile> call 1 100 # appelle Linphone A
OsmoMobile> call 1 answer # décroche
OsmoMobile> call 1 hangup # raccroche
OsmoMobile>

Arrêter : sudo /opt/osmo-launch.sh stop, ou Ctrl+C dans le terminal du banc.

Gravez, démarrez, double-cliquez.

L'ISO démarre en session live avec le bureau prêt ; l'installateur Calamares la pose sur disque, et les paquets .deb de chaque composant (osmo-operator, pont, qemu-calypso, firmware Calypso, noyau pmOS repatché) sont embarqués — l'installation se fait sans git ni réseau. L'image se construit avec build-iso.sh depuis le dépôt ; sur un Ubuntu 22.04 déjà en place, le même dépôt s'installe en natif. L'installeur en une ligne et le wiki technique restent sur la page Installeur & wiki.
